# 1.28-rc1 study release: quick test guide

Use this guide before sharing the candidate with participants. These checks have **not** been run on this APK on a device. Automated tests are recorded separately in the [release notes](../releases/1.28-rc1.md).

For every check, record **PASS**, **FAIL**, or **NOT TESTED**, the device/Android version, product barcode, network state, and what happened. Use a test account and test products, not participant records. Do not include personal information in screenshots.

## 1. Install without losing saved data

1. Before updating, open Pantry and record its item count and two saved product names.
2. Install `outputs/releases/1.28-rc1/WhatsOnMyFood-1.28-rc1.apk` over the existing release. Do not uninstall or clear app storage.
3. If Android reports an incompatible signature, stop. Use the correct distribution channel or a separate test device; uninstalling may erase study data. A Play-installed app may use a different signing certificate from this locally signed APK.
4. In Android Settings, find the app's information page and confirm version **1.28-rc1**. The Android version code is **17**.
5. Open the app. Confirm sign-in and the recorded pantry items are still present. Restart it and check again.

Expected: the update installs and existing data remains available. Do not mark the migration passed just because the APK builds.

## 2. Unlimited AI for the study

1. Open **Profile > Bitwise Plus**. Expect “Unlimited Bitwise explanations are currently enabled.” Do not buy a subscription.
2. Return to **Home > Scan a product**, keep **AI On**, and scan four different test products with complete ingredient data in one day.
3. Confirm the app does not stop the fourth explanation with a three-per-day upgrade message.

Expected: unlimited access stays enabled. A service error must be shown honestly, not treated as a successful AI result. Cached explanations do not prove that four fresh requests succeeded; record cache/service limitations separately.

## 3. Automatic checks for food recalls

1. While online, scan a test product and leave its details open without tapping **Add to Pantry**.
2. Confirm a recall check starts automatically. Open **Check food recalls** to review **Food recall status**.
3. For a successful no-match response, expect **NO KNOWN MATCH** / “No matching recall was found,” with a successful-check time. This is not a guarantee that the food is safe.
4. Separately use a package whose barcode and lot details have been checked against a current official recall. Confirm a match notice appears and **View official notice** opens the relevant record. Compare the notice with the package.
5. Rotate the screen and return to the same product. Check that the same scan does not produce duplicate dialogs.

If no verified matching package is available, record the match case **NOT TESTED**. Do not infer it passed from a no-match result or an automated fixture test. Never eat a recalled product for testing.

## 4. Pantry checks, failures, and notifications

1. Add a dedicated test product using **Add to Pantry**. Open **Pantry** and confirm it appears with recall status.
2. Tap its recall status and **Check again**. Record the successful-check time.
3. Turn off Wi-Fi and mobile data, then tap **Check again**. Expect a visible failure/unavailable/outdated status. The last successful time must not become a new successful time, and existing results must remain available.
4. Reconnect and retry. Expect recovery and an updated successful-check time.
5. In Pantry, choose **Enable recall notifications** and allow Android permission. A new matching test notice should produce one notification. Tap it to open details; repeat the check and confirm no duplicate alert for the same product/notice.
6. Also check with notification permission denied. In-app recall status must remain available. Re-enable permission and check pending-alert behavior.
7. On a dedicated test item, change product identity and confirm a new check occurs. Remove a test item during a check and confirm no stale result is attached to another item.

Daily background checks need a separate elapsed-time test. Keep the test account signed in and network available, and record when Android actually runs the work. Battery restrictions may delay it; opening the app or tapping **Check again** is not proof of the daily schedule.

## 5. Badges, translations, and product details

1. Open a product with explicit supported certification data. Confirm its matching certification artwork is shown.
2. Open a product with a generic Vegan, Vegetarian, or Gluten-Free claim. Expect a labeled app icon and **Not verified**, not a claim that certification was independently verified.
3. Open **Profile > Language**, select Spanish, and reopen the products. Expect **No verificado**, **Sin gluten**, **Vegano**, and **Vegetariano** where applicable.
4. Repeat in French: **Non vérifié**, **Sans gluten**, **Végétalien**, and **Végétarien**. Restore the original language.
5. Confirm the product-detail sections start expanded and text/buttons remain readable.

A product with no dietary/certification data does not exercise the badge case; record it as not tested and choose another test product.

## 6. Scoring and alternatives regression checks

1. Open an approved high-sugar test product and review **At a glance**, the score, findings, and AI explanation together. A score below 70 must not show a Healthy overall verdict. Missing ingredients must not produce a confident healthy verdict.
2. Choose **Compare alternatives**. Confirm the original product and returned comparison cards are readable and clearly identified.
3. Check that **LIVE RETAILER DATA** and **DEVELOPMENT SAMPLE** describe the actual provider response; simulated results must not look live.
4. Turn off the network and retry. The error message and **Try again** should remain usable, and Back should return to the product.

Do not force mock, empty, or timeout states on the shared backend. Exercise them only through an approved test environment, or record those cases as **NOT TESTED**. This smoke check does not replace the detailed M5 test procedures.

## 7. Android 16 and tablet checks

1. On Android 16, navigate Home > Scan > product > **Compare alternatives**, then use system Back. It should return one screen at a time.
2. Open a source or **View official notice**, follow a link to a second page inside the viewer, and use system Back. It should return to the prior webpage before leaving the viewer. Also test toolbar Back. Predictive-back animations are temporarily disabled to preserve the existing history handling.
3. Check that status/navigation bars do not cover Home tabs, scanner Back/photo/AI controls, product actions, **Check again**, or **Try again**. Open a Profile field and check the keyboard does not hide essential controls.
4. On the tablet, rotate portrait/landscape and try split-screen on product and recall screens. Expect no clipped actions, lost product, crash, or duplicate recall dialog.
5. If testing a 16 KB device, verify its page size first (`adb shell getconf PAGE_SIZE` must return `16384`). Exercise camera scanning, ingredient OCR, language detection, and translation, watching for native crashes. Record this separately from tests on a 4 KB device.

If no suitable device is available, leave these checks **NOT TESTED**. SDK metadata, signature checks, and passing unit tests do not establish device compatibility.
